## 2. Language families and semantic centers

| Language | Semantic center (class) | Generated/projection boundary | Extension mechanism | Versioning model | Verification strength | Likely escape hatch |
|---|---|---|---|---|---|---|
| SQL | Relational data semantics; set-at-a-time queries (schema/IDL + query) | DDL is the source of truth; migrations are generated scripts | New tables/columns, views, generated columns | Explicit migration scripts, ordered | Strong locally: constraints, FK/CHECK, plans | Stored procedures — opaque, weak |
| GraphQL | Typed request/response shape over a graph (query) | Schema → resolvers are handwritten; schema validates client queries | Additive types/fields, `@deprecated` | Continuous, additive-only; deprecations replace versions | Shape-level validation only; behavior unchecked | Custom resolvers (all behavior lives here) |
| OpenAPI | HTTP contract: paths, methods, status codes, schemas (contract/IDL) | Spec → generated client/server stubs; doc | New paths; `x-` vendor extensions | URL or header versioning; semver of spec | Schema linting, contract tests against implementations | `x-` extensions; hand-written glue |
| Protocol Buffers | Wire-stable typed message IDL (schema/IDL) | `.proto` → generated bindings per language | New fields with unique tags; `reserved` for removals | Additive, unknown-field tolerant; field tags are the ABI | Strong: compile-time + cross-language compat | `Any`, custom options, surrounding handwritten code |
| Terraform/HCL, Kubernetes | Desired-state declarative resources with reconciliation/plan (infrastructure) | Manifest → provider/controller reconciles toward state | CRDs (K8s) / providers (TF) | API group versions (`v1beta1`), state files, plan diffs | Plan/dry-run diff; CRD schema validation | Operators/controllers — full 3GL code behind the declaration |
| BPMN/DMN | Long-running process orchestration; decision tables (workflow/decision) | Diagram → engine executes; service tasks delegate | New lanes/tasks; decision-table rows | Process definition versions, instance pinning | Model checking, simulation — weak on data | Service tasks / delegates: arbitrary code |
| Terseus kernel | Typed components, ports, contracts, provenance, bounded composition (meta-language) | Declaration → checked projections into the above | New declared components binding to ports | Semver on contracts; compatibility rules kernel-checked | Whatever the target language admits, plus kernel-level checks (ports, evidence, recursion bound) | Explicit `opaque` port: pre-existing handwritten implementation, contract-checked |

Key distinction: schema/IDL languages fix *shape*; query languages fix *data access*; workflow languages fix *ordering and decision points*; infrastructure languages fix *desired state*; none fix *behavior* — behavior always falls to the escape hatch. The kernel's only reason to exist is to make that escape explicit, typed, and evidence-bound.

## 4. Extensibility and versioning stress

Task-by-task on the leading candidate per project (detailed scores above; all reasoning is static analysis, unverified by execution except where noted):

**common-tools.** (1) Core boundary = the deploy step: a K8s-style resource (or GitHub Actions workflow, which `doc.md` already sketches) expresses it exactly. (2) New provider would mean SFTP/S3 — *not* expressible in the declarative layer; it lands in the Python escape hatch, which is the correct outcome (the 006 study already rejected meta-layers here). (3) Cross-cutting change = the trailing-slash invariant: currently enforced only by prose in `doc.md` and violated by the running test suite (verified failure above). A declarative parameter with a validation schema would have made this a one-line check instead of a documented trap. (4) Workflow: trivial two-step, declarative. (5) The `/remoteassets/` join bug and the `list()`-returns-bare-names assumption are exactly the kind of edge a 4GL would *hide*; they must stay visible in the implementation layer with tests.

**lite-jnc.** (1) The stable boundary is `spec.Runner` plus the AST in `types.go` — a Protobuf-style IDL fits it: `Parser → AST` and `AST → target` become versioned message contracts. (2) New target language = new `Runner` implementation; today that is a map entry plus a struct — already good change-locality; IDL-izing the AST would keep six backends honest about what subset they consume (they currently consume nothing, since `Run()` returns `nil`). (3) Cross-cutting change = a new language feature (say, numeric literals, unchecked in `Status.md`): it ripples tokens → AST → every backend. A versioned grammar/IDL makes the ripple explicit as a schema bump, and `Status.md` becomes derived rather than hand-maintained. (4) Workflow: single-pass; BPMN would be noise. (5) The EOF-only recovery for unclosed strings is algorithmic — it stays in Go, exposed as a documented contract failure mode.

**foodsavr.** (1) Core boundary = `IRepository<T, ID>` and `Client`/`Provider`: OpenAPI for the provider REST contracts, Proto/GraphQL for the app-facing shape. (2) New grocery provider = the extension hot spot: today it means a new client class, freezed models, env keys, DI registration — an OpenAPI spec + a provider declaration table localizes most of this. (3) Cross-cutting change = e.g., making `TransactionRow` fields non-nullable or changing `Product`: Protobuf-style additive versioning plus generated freezed models gives real change-locality. (4) The import workflow (`getReceipts → getTransactionDetails → rows → Product → repository.add`) in `rema_client.dart` is a genuine multi-step composition with per-step failure modes — DMN for row→product matching rules, BPMN or kernel composition for ordering. (5) `name => prodtxt1 ?? prodtxt2 ?? 'N/A'` and per-provider header/env quirks (`Ocp-Apim-Subscription-Key`) must remain explicit overrides, not absorbed into a generic mapping.

## 6. Hybrid custom kernel design

Terseus kernel — a constrained declarative layer whose only jobs are binding, versioning, evidence, and bounded composition; it never expresses behavior.

```
# component declaration (sketch)
component RemaImport implements IImportService@1 {
  port in  txs   : schema rema/transaction@1        # typed port w/ schema
  port out sink  : schema product@2, implements ICollectionRepository@1
  contract fetch {
    requires auth.token(provider=Rema)             # precondition
    ensures  forall row in txs.rows: row.ean != null implies row.ean.isEan13
  }
  evidence  test/services/rema_import_test.dart     # must exist and pass
  version   1.3.0
}

compose ReceiptPipeline depth<=3 {
  stage fetch    = RemaImport@1.3
  stage match    = dmn rules/match_row_to_product@2
  stage persist  = RepositoryWriter(productRepository)@1
}
```

Elements:
- **Typed component**: name, version, list of typed ports.
- **Port**: direction + schema reference (schema belongs to an IDL family, not the kernel).
- **Contract**: requires/ensures predicates over port data; kernel checks syntax and binding, not truth — truth is the evidence's job.
- **Evidence**: named test/procedure that must exist, pass, and be referenced by the declaration; provenance = declaration hash + pinned source revision (here: git SHA per project, as in the 006 notes).
- **Composition**: ordered stages, each stage a component bound by contract-compatible ports.
- **Version**: semver; compatibility rule `consumer.minor <= provider.major`, checked at bind time.
- **Finite recursion measure**: every `compose` declares `depth<=k`; composition type-checks only if each stage is a leaf component or a compose with strictly smaller measure. Expansion terminates because the measure strictly decreases; the kernel rejects any declaration whose expansion budget exceeds `k` *before* projection. This is a syntactic bound, so termination is decidable.

Projection boundary: the kernel generates bindings/glue (DI registration, client skeletons, stage wiring) and emits a report listing every unbound port and unsatisfied evidence. It generates no behavior. An `opaque` port wraps existing handwritten code (e.g., `upload_dir`) behind the same contract checks. All of this is a design proposal — **nothing here has been implemented or run.**

## 7. What not to unify

- **UI semantics** (foodsavr views/widgets): no listed 4GL expresses widget trees and routing meaningfully; GraphQL covers data fetch shape only.
- **Lexer/parser state machines** (lite-jnc): algorithmic, fault-tolerance-sensitive; a declarative grammar (ANTLR-style) would be a different, real option, but the kernel must not absorb EOF-only string recovery or the `errorLimit` heuristic.
- **Business calculations** (foodsavr `utils/shelf_life.dart`): pure functions; DMN can express shelf-life *rules* but not their arithmetic cleanly.
- **The trailing-slash invariant and `list()` semantics** (common-tools): verified live failures — a unifying layer that silently normalized paths would have masked both bugs. Edge cases must fail loudly in the layer that owns them.
- **Provider quirks** (foodsavr `Ocp-Apim-Subscription-Key`, nullable REMA fields): absorbed only as explicit, reviewed per-provider overrides — never as generic machinery.
- **Cross-provider genericity for common-tools**: one FTP script; any kernel use is over-meta (consistent with the 006 L0 verdict).

## 9. Buildable language experiment

**Project:** `006-foodsavr`, bounded to `lib/features/third_party_integration/`.
**Baseline:** current hand-written `base_client.dart` + `rema_client.dart` + `coop_client.dart` + freezed models + DI registration; existing tests `test/router_auth_flow_test.dart`, `test/services/`, `test/models/`.

**Files:** declaration `lib/features/third_party_integration/providers.terseus.json`; expander `tool/gen/expand.dart`; generated output under `lib/features/third_party_integration/generated/`; new tests `test/features/generated_client_test.dart` (contract: headers, env keys, URL assembly) and `test/features/edge_case_test.dart` (asserts `name` fallback stays explicit).
**Protocol:** run `flutter test` before (baseline) and after (treatment); diff generated vs. hand-written clients; measure (a) lines added to add a fake third provider "Svea" declaration-only, (b) test pass parity, (c) whether the `prodtxt1 ?? prodtxt2` edge survives visibly.
**Acceptance criteria:** (1) adding provider "Svea" touches only a new declaration + schema file — no edits to base/expander; (2) full existing suite passes unchanged; (3) edge-case test fails if the fallback is moved into the expander; (4) declaration + expander < hand-written code it replaces (meta-size guard). Requires network for `pub get` — not executable in this environment today.

## 10. Decision and falsifiers

Decision: no single 4GL covers any of the three projects. Stacks: declarative-deploy + Python (common-tools), AST IDL + typed pipeline in Go (lite-jnc), layered OpenAPI/Proto/DMN + bounded provider registry in Dart (foodsavr). The Terseus kernel is admissible **only** in the foodsavr registry slice and the lite-jnc pipeline seam, and only as a binding/versioning/evidence layer — never as a behavior language.

Falsifiers — any of these rejects the kernel for the slice in question:
1. **Meta-size:** declaration + expander code exceeds the hand-written code it replaces for that slice.
2. **Review distance:** a reviewer shown only the declaration + expansion rules cannot predict projected behavior better than chance (protocol: quiz on three projections).
3. **Locality:** adding a new provider/target requires editing the expander or kernel core, not just a new declaration.
4. **Projection equivalence:** generated code fails any existing baseline test, or diverges semantically (headers, env keys, URL assembly) from the hand-written client.
5. **Recursion bound misfire:** `depth<=k` blocks a legitimate composition (e.g., nested import workflow) or admits any non-terminating expansion.
