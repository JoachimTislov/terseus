# 2. Abstraction-level definitions

- **L0 — concrete implementation**: source modules, functions, tests, and config are authoritative. Nothing is projected; you edit what runs.
- **L1 — typed reusable components**: explicit `Component` types with typed ports, contracts, evidence bindings, and versioned compositions. Generated/derived code is the execution projection; the component model is the review artifact.
- **L2 — recursive declarative system**: nested component/workflow declarations in a compact representation; an expander with constraints, provenance, and a finite recursion measure produces implementation projections.

**Scoring criteria (0–4), applied per dimension per project:**
- 0 = not expressible at this level without abandoning its paradigm
- 1 = expressible only via escape hatches that dominate the design
- 2 = expressible with substantial hand-written glue
- 3 = expressible natively; change is localized
- 4 = expressible natively; change is localized and mechanically checkable

Compression is inverted: 4 = ≥10x size reduction with no semantic loss; 0 = net expansion.

# 4. Extensibility stress tests

All four tests per project; affected files are observed paths. Touch counts are hand-counted estimates (~) from the file list, not edits I made.

**common-tools**
1. *Add capability* — SFTP target (`--protocol sftp`). L0: touch `ftp_client.py` (`parse_flags`, `main` constructor block), `doc.md`, `test_ftp_client.py`. ~3 files. Lower level is safer: the `ftpretty` constructor call is the only coupling point.
2. *Second provider* — swap `ftpretty` for `ftplib`. Touch `ftp_client.py:7-15` only, plus Makefile dependency line. The tests' Mock seam already anticipates this.
3. *Cross-cutting invariant* — the trailing-slash rule is currently prose in `doc.md` ("very important to include trailing slash") while `upload_dir` does raw string concat `f"{remote_directory}{file}/"`. Making it a typed path object touches every function. This is where L0 is *weakest* — an invariant lives in a comment.
4. *Nest in composite* — deploy workflow (build → test → upload). At L0 this is a shell/CI file; the system is already recursive (`upload_dir`, `delete_remote_directory`), so recursive nesting exists natively at L0 without a declarative layer.

**lite-jnc**
1. *Add capability* — new transpiler target: `transpiler/transpiler.go` (enum + `languages` map entry) + new `transpiler/<lang>.go`. ~2 files; the existing 1-line `c.go`/`java.go` placeholders prove the seam works.
2. *Second provider* — LLVM backend instead of hand-rolled x86-64: `compiler/compiler.go` (add `Compiled` case) + new backend file. README already lists this as a TODO. L0/L1 local; L2 adds nothing.
3. *Cross-cutting invariant* — standardize the AST (README TODO): touches `parser/types.go` (all node structs), `parser/parser.go` (every state function), both backends, `lexer.go` token shapes. ~6 of 14 files. This is the change L1 is designed for: a versioned AST contract turns a silent cross-cutting break into a compile error.
4. *Nest in composite* — parse → transpile → invoke external compiler: `main.go` pipeline. L0-local; L2's expander would be more code than `main.go` itself.

**foodsavr**
1. *Add capability* — third grocery provider (e.g. Salling): new `clients/salling_client.dart`, `provider_model.dart` (`Provider` enum), dotenv keys, DI auto-registration via injectable, plus `connections_list.dart` if it enumerates providers. ~3–4 files. `CoopClient` (a stub returning `[]`) is the observed template.
2. *Second provider* — SQL repositories behind `IRepository<T,ID>` (`i_repository.dart`): new repo implementations + `injection.config.dart` rebinding. The interface exists precisely for this; L0-local.
3. *Cross-cutting invariant* — change `Product` shape (`models/product_model.dart`): ripples to `product_service.dart`, `select_products_controller.dart`, all `views/product_*`, `barcode_scan_view.dart`, Rema/Coop clients, mock data (3 files), and shelf-life mapping. ~15–20 files (~, from imports I saw). Worst change-locality of all three projects; a versioned contract would make this a diff-able migration.
4. *Nest in composite* — "import receipts → create inventory → meal plan" workflow nesting `RemaClient.getProducts` inside a use-case: `import_service.dart` currently has `getReceipts/getProducts` as unrelated methods (`i_import_service.dart`); composition would be a new orchestrator service + DI entry. This is the single place where a declarative composition (one record: steps, contracts between steps, rollback) genuinely beats hand-written orchestration.

# 5. Compression versus semantic distance

| System | Best L2 compression | Semantic distance incurred |
|---|---|---|
| common-tools | ~1.2x at best (declarative "transfer task") | High: FTP error semantics, bare-except fallback, env-var contract all become implicit |
| lite-jnc | ~1.5x if the pipeline is declared | High: lexer/parser/codegen semantics are the system; declaring them duplicates them |
| foodsavr | ~3–4x within `third_party_integration` (endpoints, headers, model mappings are already table-like in `rema_client.dart` dotenv keys) | Low *there*; high if applied to views/widgets |

Rule of thumb from these three: compression is real only where the source is already tabular (endpoint maps, provider registries, duration maps like `ShelfLifeService._categoryDurations`). Semantic distance grows with every behavioral branch that the declaration must re-express as expansion rules — the moment the rule set rivals the code, L2 is a second implementation with worse diffability.

# 6. Recommended level and hybrid boundary

- **common-tools → L0.** The program is smaller than any kernel. Fix its one real weakness (path invariant) with a small function + test, not a meta-layer. L2 rejected as over-abstraction **[rejection 1]**.
- **lite-jnc → L1.** Introduce a typed AST contract + backend contracts around the existing `spec.Runner` port; keep lexer/parser/compiler as code. L2 rejected as over-abstraction **[rejection 2]**: recursive declaration of a parser state machine reproduces the machine in a worse language.
- **foodsavr → L1 core, bounded L2 at one seam.** Formalize components/contracts over the existing interface layer; permit a declarative provider-specification kernel *only* for `features/third_party_integration` (and optionally receipt-import workflow composition). Widgets, controllers, and Firebase services stay code.

Hybrid boundary rule: a subsystem may use the declarative kernel iff (a) its data is naturally tabular, (b) it has <N≈10 declaration kinds, and (c) every declaration expands to code that existing tests already know how to mock (the `Client.fetch`/`Mock` seam).

# 7. Reusable declaration kernel

Model proposal (TypeScript-flavored pseudo-typing; no implementation exists):

```ts
type Port = { name: string; type: string;              // e.g. "http.GET"
              direction: "in" | "out" };
type Contract = { id: string; version: string;        // semver, breaking = major
                  pre?: Predicate; post: Predicate;   // typed predicates
                  onViolation: "error" | "rollback" };
type Evidence = { kind: "test" | "bench" | "check" | "manual";
                  ref: string;                         // path or CI run id
                  covers: string };                     // contract id
type Component = { id: string; version: string;
                  ports: Port[]; contracts: Contract[];
                  evidence: Evidence[];
                  projection: { lang: string; target: string } };  // generated code
type Composition = { id: string; version: string;
                    steps: { component: string;         // id@version — DAG, not tree
                              binds: { port: string; to: string }[] }[];
                    budget: { maxDepth: number;        // e.g. 8
                              maxWidth: number;        // steps per level, e.g. 64 } };
```

**Finite recursion measure:** each `Composition.budget` is fixed at declaration; expansion is defined only as `expand(c, depth, width)` where `depth` decreases strictly toward 0 and `width` bounds fan-out per level, so every expansion terminates in ≤ `maxDepth × maxWidth` nodes. Nesting a composition inside a composition consumes the parent's budget (provenance tracks the chain), preventing the infinite-regress failure mode L2 systems usually hit.

**Worked example — foodsavr `RemaClient` as a Component (proposal, grounded in observed code):**
- Ports: in `http.GET` (the `fetch(env, suffix)` method, `base_client.dart`), in `secure.read` (`SecureStorage.read(provider, Key.access_token)`), out `products` (`List<Product>` from `getProducts(userId)`).
- Contract: `receipts→products v1`: post = "every emitted Product has non-null id, barcode, description" — exactly the guard already hand-coded in `rema_client.dart` (`if (id != null && barcode != null && description != null)`); pre = "REMA_API_SUB_KEY and REMA_TRANSACTIONS env keys resolve".
- Evidence: the DI binding plus a proposed contract test (not the existing suite, which doesn't cover RemaClient).
- Composition: `receipt-import v0.2`: steps `rema-client@1.x` → `import-service@1.x` → `inventory-repo@1.x`, budget `{maxDepth: 2, maxWidth: 4}` — one level of nesting, terminates.

# 8. Verification and provenance requirements

1. Every `Contract` must list ≥1 `Evidence` of kind `test` before a composition referencing it validates. (Currently violated in all three repos: lite-jnc's only test is commented out; common-tools' tests don't cover `delete_remote_directory`'s bare `except:`; foodsavr has no RemaClient test — observed.)
2. Provenance: each generated projection records generator version, source declaration hash, and component versions; regenerating with unchanged hashes must be byte-stable.
3. Contract version bumps: major = composition must re-validate; minor/patch = automatic.
4. Expansion must emit a termination proof (depth trace) alongside code; CI rejects projections without one.
5. Escape hatches (hand-written code inside a component) are allowed but counted; a component with >30% escape-hatch code fails the "why is this a component" check — this is what keeps lite-jnc's lexer out of the kernel.
